## What PuzzleScript is

The games in this environment are written in PuzzleScript, a small, open-source scripting language designed for making two-dimensional, tile-based puzzle games in the lineage of Sokoban. A PuzzleScript game is a single text file. That file declares a set of objects (each with a name, a colour palette, and a 5×5 pixel sprite), a legend that maps single characters to objects or combinations of objects, a list of collision layers, a list of rewrite rules, a set of win conditions, and a sequence of levels drawn as ASCII art. The whole engine is deterministic: given a state and an input, the next state is fully determined.

Every game runs on a rectangular grid. Each grid cell can hold several objects at once, but only one object per collision layer. The layering is declared explicitly in the source: a typical arrangement puts the background on the bottom layer, floor decorations such as targets or buttons on a middle layer, and solid things like the player, walls, and crates on a top layer that they share and therefore cannot overlap within. Two objects that are on different layers can occupy the same cell; two objects on the same layer cannot.

The player is an ordinary object like any other, distinguished only by being the thing the engine moves in response to directional input. If a level contains several player objects, every one of them receives the same input on the same turn. Nothing in the language prevents a game from having two, five, or thirty "players" who all attempt to step left when the left key is pressed.

The rules section is a list of pattern-rewrite rules. Each rule has a left-hand pattern of cells and a right-hand replacement. Patterns are written as a row of cells separated by `|`, and can be matched in any of the four directions unless the rule is restricted with a prefix like `horizontal`, `vertical`, `down`, or `up`. Objects in a pattern can carry a movement marker (`>` for "moving in the rule's direction", `<` for the opposite, `^` and `v` for the perpendiculars, and `stationary`), so a rule can say things like "when a player moving toward a crate is adjacent to that crate, make the crate also move in that direction." The canonical push rule, present in nearly every game here in some form, is `[ > Player | Crate ] -> [ > Player | > Crate ]`. Rules are applied in order, repeatedly, until nothing changes; then all pending movements are resolved (a movement into a cell already occupied on the same layer simply fails); then any rules marked `late` are applied to the settled board. After that, the win conditions are checked.

There are also some whole-game flags that appear in the sources. `noaction` removes the action button from the game entirely. `run_rules_on_level_start` causes the rule set to execute once before the player's first turn, which is how some games construct derived state (shadow sprites, beams, colour floods) from the raw level drawing. `throttle_movement` only affects real-time input timing and has no bearing on turn-based play. `again` is a rule command that causes the engine to take an additional automatic turn with no input, which is how some games produce countdowns or chain reactions.

Win conditions are declared as simple quantified statements: `all X on Y`, `some X on Y`, `no X on Y`, `some X`, `no X`, and so on. Every game in this corpus uses only the `all X on Y` form. A game may stack several such conditions, and all of them must hold simultaneously for the level to be won. Importantly, the condition is checked each turn against the whole board; if there are zero instances of X on the board, `all X on Y` is trivially satisfied. The direction of the statement varies between games: in some it is `all Player on Goal`, in others `all Goal on Player`, and these are not interchangeable when there are more players than goals or vice versa.

Levels are drawn as rectangles of characters, each character being one entry from the legend. A legend entry can stand for a single object or for a stack of objects in one cell (for example, "a crate and a target and a ground tile"). Between levels, authors frequently insert `message` lines: titles, hints, jokes, or narrative. In normal play these messages are displayed on screen between levels.

## What the player experiences

The player in this environment does not see any of the above. They are not shown the source file, the rules, the win conditions, the legend-to-object mapping used by the author, the inter-level messages, or the level number. They are dropped directly into a single level of a single game and told only that it is a grid puzzle whose rules must be inferred from acting and observing.

The text the player receives on turn zero is always the same template. It states that the rules are not given, that the objective is to reach the game's win condition, that the available actions are `up`, `left`, `down`, `right`, `action`, `undo`, and `restart`, and that `action` is a generic button which in some games does nothing. It then explains the grid format and provides a legend, followed by the grid itself.

The grid is rendered as rows of cells separated by `|`. Each cell is a fixed-width string of characters, one slot per character. The number of slots is the same for every cell in the level and equals the maximum number of objects that co-occupy any single cell at that moment. A slot containing `.` is empty. So in a level where no cell ever holds more than one object, each cell is a single character and the row looks like `W|.|.|P|.|W`. In a level where some cell holds five objects at once, every cell is five characters wide, with most of them padded by dots: `VB...|GTB..|VPCMB`.

The legend given to the player is generated from the object names in the source, lowercased. Each object present on the opening board is assigned a single uppercase letter. The letter is usually the first letter of the object's name, but when two objects would collide on the same letter, one of them is given some other letter. The result is that the character shown for a thing is not always mnemonic: a goal may be labelled `C` because `G` was already taken by a grate; a target may be labelled `A` because `T` went to a different object; a player object might be `E` because `P` was consumed by a timer object whose name happened to be sorted earlier. The legend lists only objects that are on the board at the start. Objects that come into existence later through rules — a transformed player carrying a key, a new colour produced by mixing, a door that has turned into an open doorway, a dropped marker — are not in the initial legend.

The background object is omitted from the rendering; a cell containing only background shows as a single `.`. Everything else is shown, including objects that in the original game are invisible. PuzzleScript authors often use transparent objects as bookkeeping: markers that remember where a box started, markers that record which cell holds the countdown, invisible beams that connect a special crate to the ground tiles it drags. In the browser version of the game the human player never sees these. In this environment they are rendered as ordinary letters, sitting in cells alongside visible objects. The player therefore sees more of the machinery than the author intended, but without any explanation of what the extra letters mean.

The order of characters within a cell follows the layer ordering of the source rather than any visual priority, so the "important" solid object in a cell is not necessarily listed first.

## Turns, actions, and ending

Each turn the player submits one action. The four directions attempt to move every player object one cell in that direction, with whatever consequences the rules produce. `action` is PuzzleScript's fifth input; some games bind rules to it, and games with the `noaction` flag ignore it altogether. In the corpus here, several games carry `noaction`, and none of the remaining games define a rule that reads the action key, so the action button has no effect in any of the sampled games — though the player is not told this, and the only way to learn it is to press it and see nothing change.

`undo` reverts the board to the state before the previous action. `restart` returns the level to its opening state. Both of these consume a turn from the budget but are otherwise free of in-game consequences. Some games also contain their own restart mechanisms: a rule that fires `restart` when a certain condition is met, which returns the level to its starting configuration in the middle of play without the player having asked for it.

The episode ends in one of two ways: the win conditions become satisfied after some turn, or the player exhausts a fixed turn budget. The budget is not stated to the player. The optimal solutions to the sampled levels are all short — between five and twelve moves — so the budget is not the binding constraint for a player who understands the puzzle, but it does limit how much exploratory flailing is affordable.

When a level is won, nothing more is shown; there is no next level. The sampled level is the entire episode. There are also no inter-level messages. The sources are full of hints like "sponges can wipe up color", "Rocks get IN YOUR WAY!!", "Take your time, this one could take a while", or "Put the battery in the outlet", and in normal play those would have scaffolded the player's understanding. Here they are all stripped.

## Where the sampled levels come from

Each task is a single (game, level) pair. Levels are sampled from throughout the games' level lists, not just from the beginning. One task is level 126 of a game that has over a hundred levels; the player arrives having seen none of the preceding 125 and none of the tutorial messages. Another task is level 41 of a game whose levels are interleaved with a running narrative about jobs and paychecks. Others are levels one through six of their games. The level index in the task name is a flat count that includes message screens, so it does not correspond cleanly to the author's own numbering.

The games vary enormously in complexity as measured by their rule count. The simplest has a single rule — the push rule — and nothing else; all the puzzle content comes from level geometry and from having multiple player objects. The most complex has nearly forty rules implementing a countdown timer, a board reset that restores boxes and the player to their starting positions while preserving collected powerups, a box-destruction ability, and a double-move ability. Most games fall between five and twenty rules.

The grids vary in size too. The smallest sampled opening grid is three columns by eight rows. Others are around seven by seven, nine by five, ten by five, and the largest is twenty columns wide. Some levels are fully enclosed by a wall border; others have open edges where the grid simply stops (PuzzleScript treats the grid edge as impassable). Several levels are made of multiple disconnected rooms, each containing its own player and its own goal.

## The kinds of mechanics present

Although the player sees none of the rules, it is useful to describe the family of mechanics that occurs across the corpus, since this is the distribution from which a task is drawn.

**Pushing.** Almost every game has Sokoban-style pushing: walking into a movable object shoves it one cell in the walking direction, provided the cell beyond is free. The variations are where the interest lies. In one game, several of the pushable classes can be pushed only horizontally or only vertically. In another, a chain of stones can be pushed as a unit, stone into stone into stone, but a stone cannot be pushed onto a grate tile or into a closed door. In another, crates refuse to move onto an "edge" tile or onto already-painted floor. In another, pushing is blocked unless the cell beyond is solid ground rather than void.

**Multiple simultaneous players.** One game's entire conceit is that every level contains several player objects, often in separate rooms, and all of them move together. The win condition is that every goal has a player on it. Since the players are in different-shaped rooms with crates and walls placed asymmetrically, the same sequence of inputs moves them along different paths; a wall that stops one clone lets the others continue, and this is the only way to desynchronise them. The sampled level has two rooms, one with a crate in the way and one without. Other games also have levels with more than one player, used for the same purpose.

**Disappearance by matching.** One game removes any three identical crates that end a turn in a straight line of three adjacent cells. Its win conditions require every crate of several kinds to be on a "dump" tile, so for most levels the practical route is to eliminate crates in threes until none remain, making the condition vacuously true. The same game also has coloured "bar" blocks that must be pushed onto correspondingly shaped "battery" tiles, a key that transforms the player into a key-carrying variant, locks that a key-carrying player can walk through (consuming the key and destroying the lock), and immovable rocks. The sampled level from this game is one of the smallest in the corpus: a player above a row of rocks, with four vertically-only crates below.

**Colour mixing.** One game is built around pushing coloured crates into each other. When a crate of one primary colour is pushed into a crate of a different primary, both vanish and a single crate of the secondary colour appears where the second one was. Pushing a primary into the complementary secondary produces a crate labelled "white" (though its sprite is drawn in black). The targets on the floor are colour-coded, and the win requires each target to be covered by a crate of the matching colour. In the sampled level there is one red crate, one red target, a player, and a wall partition with a gap exactly where the target sits.

**Buttons, doors, and grates.** One game has pressure buttons that open a matching-colour door while a stone sits on them; lifting the stone closes the door again. Doors are solid when closed and become a distinct floor object when open. Grate tiles can be walked on but block stones. The sampled level has no buttons at all: it is an arrangement of stones, grates, and a goal, where the player must thread a path through the stones using pushes that are constrained by the grates and the grid edge.

**Teleporters.** One game has a teleporter tile that projects the player (or a crate) in the direction of travel across all intervening cells until the first free cell past any solid object. Walking onto a teleporter in a given direction effectively jumps the mover along that line. The same game has monsters that are solid, and a late rule that kills the player — triggering a full level restart — if a monster is adjacent to the player at the end of a turn. The sampled level has a row of monsters between the player and the goal, with a line of teleporters below them.

**Flood-fill paint.** One game treats pushable crates as paint sources: certain crates, when pushed onto an open floor, leave a flood of colour that spreads downward first and then outward into every connected floor cell not blocked by an edge tile or a crate. Two floods of different primary colours merging turn the whole merged region into the secondary; three primaries make brown "mix". A sponge crate wipes up paint as it is pushed. The floor has coloured goal markers, and the win requires each goal marker to be covered by paint of that exact colour. The sampled level is a narrow vertical shaft with a blue source crate at the top, several crates in the channel, and a column of blue goal markers on the right.

**Countdown and reset.** One game has a visible countdown digit in the corner. Every turn it decrements; when it reaches zero, the board resets: the player returns to its start marker, every box returns to its start marker, and the timer returns to its initial value. However, powerup tiles collected during the countdown persist across resets as permanent abilities stored in the wall corner: one lets the player destroy boxes by walking into them, another lets the player move two cells per turn. The sampled level has a timer of nine, a column of three boxes between the player and the goal, no visible powerup, and dead-end alcoves. Because the markers and timer are rendered, the opening grid contains several transparent-marker letters that would be invisible in the original.

**Item transformation and destruction.** One game has a battery item that must be pushed onto an outlet target, a drained battery that must be pushed onto a charging target, a red item that destroys any battery pushed into it, a green item that transforms into a battery when the player walks into it, and a lightning item that recharges a drained battery pushed into it. The sampled level is a small open room with one of each of several item types and a single outlet.

**Beams and moving ground.** One game has islands of ground floating in void. A special crate, when pushed, drags with it a chain of invisible "beam" objects and the "magic" ground tiles they are connected to, so that pushing the special crate slides a patch of floor across the void. Ordinary crates sitting on that patch ride along. The player cannot step into void. The sampled level has two islands separated by void, a special crate on the left island, a magic patch in the gap, a regular crate, and a target on the right island. Because beams are rendered, nearly every cell in the opening grid shows a `B`.

**Keys, locks, and rocks.** As mentioned, one game includes keys that the player picks up by walking over them (changing the player into a different object), locks that only a key-holder can pass, and rocks that are pushable but never disappear and never count for anything.

## Common structural features

A few regularities hold across the whole corpus and shape what a blind player encounters.

Every game's win condition is of the form "all of one thing on another thing", and in every sampled level the two things are visible on the opening grid: a goal and a player, targets and crates, coloured markers and coloured blocks. There are no sampled levels where the win condition refers to an object that has not yet appeared.

In every game, walls are completely immovable and impassable. Walls are typically rendered with `W`, though in the painted-floor game walls share a letter with an "edge" object and a "side" shadow object that are drawn separately.

In every game, the player object moves only when a direction is pressed; there is no gravity, no drifting, no enemies that move on their own. The only non-player things that change without a push are late-rule effects: timers ticking, paint spreading, matches vanishing, doors toggling, and reset events.

Nearly every game has a Sokoban-style push as its first rule. The differences are in what can be pushed, in which directions, into what, and what happens afterward. Several games forbid pushing a chain of two objects; a couple allow it.

Several games involve objects that are consumed, destroyed, or transformed on contact. These are irreversible within the forward timeline, though `undo` reverts them.

The sampled levels are consistently small in solution length. The optimal solutions range from five to twelve moves, meaning that the level can in principle be solved within a dozen inputs by someone who knows exactly what to do. This is not the same as the levels being easy to understand: the twelve-move solution to the moving-ground level depends on grasping a mechanic that has no analogue in ordinary Sokoban, and the nine-move solution to the countdown level requires recognising that the timer is a resource.

## The information gap

The defining feature of the setting is the gap between what the source contains and what the player sees. An author's PuzzleScript file encodes, in a few hundred lines, everything about how the world works: that a stone cannot go on a grate, that three crates in a row vanish, that red plus blue makes purple, that a monster adjacent at end-of-turn means death. The player receives none of it. They receive a grid of uppercase letters with a legend that gives each letter a lowercased name — "cratespecial", "tred", "item3", "grate", "playermarker", "timer9" — and the names are the only semantic hint available. Some names are informative (`goal`, `wall`, `monster`, `tele`). Some are opaque (`item4`, `b`, `crate10`, `side`). Some are misleading relative to the letter chosen to represent them.

What the player does have is the ability to act and watch. Every action produces a new rendering of the full grid, so changes anywhere on the board are visible: a crate moved, a letter vanished, a new letter appeared, a digit in the corner decremented, a cell that was padded with dots now full of objects. The counter-factual tools `undo` and `restart` allow experiments to be reversed. The turn budget bounds the total amount of experimentation plus solution.

The setting is therefore a particular kind of inference problem layered over a particular kind of puzzle problem: the hidden rules are always simple, always deterministic, always expressed as local cell-pattern rewrites, and always drawn from a family of mechanics recognisable to anyone familiar with the block-pushing genre — but they must be discovered through interaction, and the level then solved, within a modest number of turns, without any of the explanatory scaffolding the game's author provided.
